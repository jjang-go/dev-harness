# 브랜치 전략: GitHub flow

`main` 하나만 장기 브랜치로 두고, 모든 변경을 짧은 브랜치와 PR로 합치는 단순한 전략이다. 지속적 배포에 알맞다.

## 브랜치 구조

| 브랜치 | 역할 | 분기 | 병합 대상 |
| --- | --- | --- | --- |
| `main` | 항상 배포 가능한 상태를 유지한다. | - | - |
| `feature/*`, `fix/*` 등 | 하나의 목적을 가진 작업 | `main` | `main` |

## 브랜치 이름

- `<타입>/<짧은-설명>` 형식을 쓴다. 타입은 `feature`, `fix`, `refactor`, `docs`, `test`, `chore` 중에서 고른다.
- 설명은 소문자와 `-`로 이어 쓰고, 한 프로젝트에서는 한 가지 언어로 통일한다.
- 이름만 보고 무슨 작업인지 알 수 있게 짓는다.

## 작업 흐름

1. `main`에서 브랜치를 만든다. 서로 무관한 변경은 브랜치를 따로 쓴다.
2. 커밋은 하나의 완결된 변경 단위로 나눠 자주 하고 자주 푸시한다.
3. 피드백이 필요하면 PR을 연다. 미완성이면 draft로 연다. PR에는 변경 내용과 해결하는 문제를 적고 관련 이슈를 연결한다.
4. 상태 체크가 통과해야 하고, 리뷰 의견은 같은 브랜치에 커밋을 추가해 반영한다.
5. 승인을 받으면 `main`에 병합하고 브랜치를 삭제한다.
6. 병합 뒤 `main`에서 배포한다.

## 병합 방식

- 기본은 squash 병합이다. PR 하나가 `main`에 커밋 하나로 남는다.
- squash 커밋 메시지는 커밋 메시지 규칙을 따른다.
- 이미 공유된 브랜치의 이력을 rebase나 force push로 다시 쓰지 않는다.

## Claude가 지킬 것

- `main`에 직접 커밋하거나 푸시하지 않는다. 항상 작업 브랜치에서 한다.
- 새 작업은 최신 `main`에서 브랜치를 만든다.
- 한 브랜치에는 하나의 목적만 담고, 무관한 변경이 섞이면 나눈다.

## 저장소 설정 권고

- `main`에 브랜치 보호를 걸어 리뷰 승인과 상태 체크 통과를 필수로 한다. 이 설정은 규칙으로 강제할 수 없으므로 저장소 설정에서 직접 한다.
