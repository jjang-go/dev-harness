# 브랜치 전략: Gitflow

릴리스 주기가 있고 여러 버전을 관리하는 프로젝트를 위한 전략이다. 개발과 릴리스를 브랜치로 분리하므로 지속적 배포에는 무겁다.

## 브랜치 구조

| 브랜치 | 역할 | 분기 | 병합 대상 |
| --- | --- | --- | --- |
| `main` | 릴리스된 코드만 둔다. 모든 커밋에 버전 태그를 붙인다. | - | - |
| `develop` | 다음 릴리스를 위한 통합 브랜치 | `main` | - |
| `feature/*`, `fix/*` 등 | 기능·수정 작업 | `develop` | `develop` |
| `release/<버전>` | 릴리스 준비와 안정화 | `develop` | `main`, 그 뒤 `develop` |
| `hotfix/<버전>` | 운영 중인 버전의 긴급 수정 | `main` | `main`, `develop` 양쪽 |

## 브랜치 이름

- `<타입>/<짧은-설명>` 형식을 쓴다. 타입은 `feature`, `fix`, `refactor`, `docs`, `test`, `chore` 중에서 고른다.
- 설명은 소문자와 `-`로 이어 쓰고, 한 프로젝트에서는 한 가지 언어로 통일한다.
- 릴리스와 핫픽스는 `release/1.2.0`, `hotfix/1.2.1`처럼 버전을 이름에 넣는다.

## 작업 흐름

1. 기능·수정 브랜치는 항상 `develop`에서 만든다.
2. 작업이 끝나면 PR로 `develop`에 병합한다.
3. 릴리스할 때 `develop`에서 `release/<버전>`을 만든다. 이 브랜치에는 버그 수정, 버전 갱신, 문서만 넣고 새 기능은 넣지 않는다.
4. 릴리스가 확정되면 `main`에 병합하고 버전 태그를 붙인 뒤, 같은 브랜치를 `develop`에도 병합하고 삭제한다.
5. 운영 중 긴급 수정은 `main`에서 `hotfix/<버전>`을 만들어 고친다. `main`에 병합하고 태그를 붙인 뒤 `develop`에도 병합하고 삭제한다.

## 병합 방식

- 모든 병합은 `--no-ff`로 병합 커밋을 남겨, 브랜치가 어디서 갈라지고 합쳐졌는지 이력에 보이게 한다.
- 이미 공유된 브랜치의 이력을 rebase나 force push로 다시 쓰지 않는다.
- 병합이 끝난 작업 브랜치는 삭제한다.

## Claude가 지킬 것

- `main`과 `develop`에 직접 커밋하거나 푸시하지 않는다. 항상 작업 브랜치에서 한다.
- 브랜치를 만들기 전에 기준 브랜치를 확인한다. 기능·수정은 `develop`, 핫픽스는 `main`이다.
- 핫픽스와 릴리스를 병합할 때 `develop` 반영을 빠뜨리지 않는다.

## 저장소 설정 권고

- `main`과 `develop`에 브랜치 보호를 걸어 PR과 상태 체크 통과를 필수로 한다. 이 설정은 규칙으로 강제할 수 없으므로 저장소 설정에서 직접 한다.
