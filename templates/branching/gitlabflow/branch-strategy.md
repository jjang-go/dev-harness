# 브랜치 전략: GitLab flow (환경 브랜치형)

`main`에서 개발하고, 환경 브랜치를 따라 상위에서 하위로 변경을 흘려보내 배포하는 전략이다. 어떤 브랜치가 어느 환경에 배포됐는지 분명하게 하려는 목적이다.

## 브랜치 구조

| 브랜치 | 역할 | 분기 | 병합 대상 |
| --- | --- | --- | --- |
| `main` | 개발의 기준 브랜치. 모든 변경이 먼저 들어온다. | - | - |
| `pre-production` | 운영 전 검증 환경에 배포된 코드 | `main` | - |
| `production` | 운영 환경에 배포된 코드 | `pre-production` | - |
| `feature/*`, `fix/*` 등 | 하나의 목적을 가진 작업 | `main` | `main` |

- 환경 브랜치 이름은 프로젝트의 환경에 맞게 바꿀 수 있다. 바꾸면 이 파일의 이름도 같이 고친다.
- 외부에 버전을 배포해야 하는 프로젝트만 `2-3-stable` 같은 릴리스 브랜치를 추가로 둔다.

## 브랜치 이름

- `<타입>/<짧은-설명>` 형식을 쓴다. 타입은 `feature`, `fix`, `refactor`, `docs`, `test`, `chore` 중에서 고른다.
- 설명은 소문자와 `-`로 이어 쓰고, 한 프로젝트에서는 한 가지 언어로 통일한다.

## 작업 흐름

1. 작업 브랜치는 `main`에서 만들고, PR로 `main`에 병합한다.
2. `main`에서 검증이 끝나면 `pre-production`에 병합하고, 거기서 검증이 끝나면 `production`에 병합한다. 병합 방향은 항상 `main` → `pre-production` → `production`이다.
3. 긴급 수정도 `main`에 먼저 반영한 뒤 환경 브랜치로 내려보낸다. 환경 브랜치에서 먼저 고치지 않는다. 모든 환경에서 같은 수정을 거치게 하기 위해서다.
4. 릴리스 브랜치를 쓴다면 수정은 `main`에 먼저 반영하고 cherry-pick으로 가져오며, 심각한 버그 수정만 허용한다.

## 병합 방식

- 작업 브랜치를 `main`에 합칠 때는 squash 병합을 기본으로 한다.
- 환경 브랜치로 올릴 때는 squash하지 않고 병합 커밋으로 합친다. squash하면 브랜치 간 관계가 끊겨 무엇이 배포됐는지 이력으로 확인할 수 없다.
- 이미 공유된 브랜치의 이력을 rebase나 force push로 다시 쓰지 않는다.

## Claude가 지킬 것

- `main`과 환경 브랜치에 직접 커밋하거나 푸시하지 않는다. 항상 작업 브랜치에서 한다.
- 변경을 환경 브랜치에 먼저 넣지 않는다. 항상 `main`부터 시작하고 아래 방향으로만 병합한다.
- 새 작업은 최신 `main`에서 브랜치를 만든다.

## 저장소 설정 권고

- `main`과 환경 브랜치에 브랜치 보호를 걸고, 환경 브랜치는 병합 권한을 제한한다. 이 설정은 규칙으로 강제할 수 없으므로 저장소 설정에서 직접 한다.
