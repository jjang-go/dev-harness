# 브랜치 전략: 트렁크 기반 개발

모든 개발자가 `main`(트렁크) 하나에 자주 통합하는 전략이다. 브랜치를 오래 두지 않아 통합 충돌과 릴리스 부담을 줄인다.

## 브랜치 구조

| 브랜치 | 역할 | 분기 | 병합 대상 |
| --- | --- | --- | --- |
| `main` | 트렁크. 항상 릴리스 가능한 상태를 유지한다. | - | - |
| `feature/*`, `fix/*` 등 | 수명이 짧은 작업 브랜치 | `main` | `main` |
| `release/<버전>` | 선택 사항. 릴리스를 안정화해야 할 때만 쓴다. | `main` | - |

## 브랜치 이름

- `<타입>/<짧은-설명>` 형식을 쓴다. 타입은 `feature`, `fix`, `refactor`, `docs`, `test`, `chore` 중에서 고른다.
- 설명은 소문자와 `-`로 이어 쓰고, 한 프로젝트에서는 한 가지 언어로 통일한다.

## 작업 흐름

1. 작업은 작게 쪼개 하나의 브랜치가 24시간 안에 `main`에 병합되게 한다. 하루에 한 번 이상 통합하는 것이 기준이다.
2. 푸시하기 전에 로컬에서 전체 빌드와 테스트를 통과시킨다. PR에서는 CI가 다시 검증한다.
3. PR은 작게 유지하고 리뷰는 바로 받는다. 리뷰가 지연되면 브랜치가 길어지므로 다른 일보다 먼저 처리한다.
4. 아직 끝나지 않은 기능은 브랜치를 길게 끌지 말고 feature flag나 추상화 뒤에 숨겨 `main`에 병합한다. 하나의 기능에 플래그가 많이 필요하면 작업을 더 쪼갠다.
5. 릴리스 브랜치를 쓴다면 `main`에서 필요한 시점에 만들고, 수정은 `main`에 먼저 반영한 뒤 cherry-pick으로 가져온다. 릴리스가 끝나면 삭제한다. 쓰지 않는다면 `main`에서 바로 릴리스하고 문제는 다음 커밋으로 고친다.

## 병합 방식

- 기본은 squash 병합이다. 브랜치가 짧으므로 PR 하나가 `main`에 커밋 하나로 남는다.
- 이미 공유된 브랜치의 이력을 rebase나 force push로 다시 쓰지 않는다.
- 병합한 브랜치는 바로 삭제한다.

## Claude가 지킬 것

- `main`에 직접 커밋하거나 푸시하지 않는다. 아무리 작은 변경도 짧은 브랜치와 PR을 거친다.
- 로컬에서 병합한 뒤 푸시하는 것도 직접 푸시와 같다. PR을 만드는 데까지 하고 병합은 사용자가 한다. 사용자가 병합을 요청하면 플랫폼의 병합 기능으로 위 병합 방식을 지정해 병합한다. 리뷰와 CI를 거치지 않은 변경이 `main`에 들어가지 않게 하기 위해서다.
- 작업 범위가 하루 안에 끝나기 어렵게 커 보이면 브랜치를 만들기 전에 더 작은 단위로 나눌 것을 제안한다.
- 미완성 변경을 `main`에 넣어야 하면 플래그 등으로 동작을 숨기고, 숨기지 않은 채 병합하지 않는다.

## 저장소 설정 권고

- `main`에 브랜치 보호를 걸어 PR과 CI 통과를 필수로 한다. 이 설정은 규칙으로 강제할 수 없으므로 저장소 설정에서 직접 한다.
