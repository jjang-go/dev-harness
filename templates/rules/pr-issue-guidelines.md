# PR·이슈·기능 명세 작성 규칙

PR(MR)과 이슈, 기능 명세는 사람과 에이전트가 이후에 읽고 그대로 작업하는 문서다. 읽는 쪽이 추측하지 않아도 되도록 아래 규칙을 따른다.

## 공통

- 저장소에 템플릿이 있으면 그 템플릿의 항목과 순서를 그대로 따른다. 항목을 임의로 지우거나 이름을 바꾸지 않는다. 해당 없는 선택 항목만 지운다.
- 템플릿의 `필수` 표시 항목은 비워 두지 않는다.
- 확인하지 않은 사실을 확인한 것처럼 쓰지 않는다. 모르는 것은 모른다고 적는다.

## PR(MR)

- 개요에는 무엇을 했는지보다 왜 했는지를 쓴다.
- 하나의 PR에는 하나의 목적만 담고, 무관한 변경은 나눈다.
- 검증 항목에는 실제로 실행한 확인만 적는다. 확인하지 못한 부분은 그렇게 적는다.
- 관련 이슈가 있으면 닫기 키워드(`Resolves #123`, GitLab은 `Closes #123`)로 연결한다.
- 제목은 커밋 메시지 규칙의 제목 형식을 따른다.

## 이슈

- 에이전트가 이슈만 보고 작업을 끝낼 수 있게 쓴다.
  - 정확한 파일, 함수, 엔드포인트 이름을 적는다. 막연한 목표만 쓰지 않는다.
  - 수용 기준은 실행하거나 관찰해서 확인할 수 있는 조건으로 쓴다. 가능하면 통과해야 하는 테스트 이름을 적는다.
  - 종료 조건을 적는다. 언제 작업을 멈춰도 되는지 모르면 작업이 끝나지 않는다.
  - 수정해도 되는 범위와 건드리면 안 되는 범위를 구분한다.
- 버그 이슈는 재현 단계, 기대 동작, 수용 기준이 필수다. 기대 동작은 구체적인 예로 쓴다.
- 기능 요청 이슈는 문제와 수용 기준이 필수다. 해결책이 아니라 문제를 쓴다.

## 기능 명세

- 구현 전에 필요한 상세 내용은 이슈에 몰지 않고 `docs/specs/` 아래 명세 문서로 분리해 이슈에서 링크한다. 명세는 `docs/specs/TEMPLATE.md`를 복사해 쓴다.
- 사용자 시나리오는 우선순위를 매기고, 각각 단독으로 검증할 수 있게 Given/When/Then으로 쓴다.
- 요구사항(`FR-001`)과 성공 기준(`SC-001`)에는 번호를 붙인다. 성공 기준은 구현 기술과 무관한 측정 가능한 결과로 쓴다.
- 구현 방식은 명세에 적지 않는다. 무엇을 왜 만드는지와 어떻게 확인하는지를 적는다.
- 정해지지 않은 내용은 추측해 채우지 않고 `[확인 필요: 질문]`으로 남긴다. 구현을 시작하기 전에 이 표시를 해소한다.
- 이번 범위에 넣지 않는 것은 비목표에 적는다.
